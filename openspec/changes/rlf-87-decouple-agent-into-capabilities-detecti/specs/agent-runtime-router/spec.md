# agent-runtime-router spec delta — RLF-87

## ADDED Requirements

### Requirement: Agent runtime MUST separate structural phase from behavioral gate

`derivePlanPhase` (in `packages/core/src/openspec/phase.ts`) MUST return one of `proposal | design | tasks | implement | done` and MUST NOT return `awaiting-confirmation`. Whether the confirmation gate is active MUST be derived from feature state (`state.confirmation.confirmedAt`) by `features/confirmation/detect.ts:gateActive(...)`, NOT from the structural phase.

Once `state.confirmation.confirmedAt !== null`, `gateActive` MUST return `false` for the remainder of the change's lifetime, regardless of subsequent edits to `tasks.md` (including additions of unchecked items by recovery flows).

#### Scenario: Phase derivation never returns the legacy gate value

- **Given** any `openspec/changes/<name>/` layout the agent encounters
- **When** `derivePlanPhase(layout)` is invoked
- **Then** the returned value is one of `proposal | design | tasks | implement | done`
- **And** it is NOT `awaiting-confirmation`

#### Scenario: Confirmed change is not re-gated by a recovery flow

- **Given** `state.confirmation.confirmedAt` is a non-null timestamp
- **And** a `conflict-fix` flow has just appended an unchecked task to `tasks.md`
- **When** the next poll runs detections
- **Then** `gateActive(state)` returns `false`
- **And** the router assigns `conflict-fix` (NOT `confirmation`)

### Requirement: Router MUST be a pure total function with explicit precedence

`runtime/router.ts:route(signals, state)` MUST be a pure function — no I/O, no `Date.now()`, no state mutation. It MUST be total over the `Signals` shape, returning a defined `FlowAssignment` for every input. Precedence MUST place `conflict-fix` and `ci-fix` strictly above `confirmation`.

#### Scenario: Conflict signal beats confirmation gate

- **Given** `signals.confirmation.gateActive === true`
- **And** `signals.conflict.prConflicted === true`
- **When** `route(signals, state)` is invoked
- **Then** the returned assignment's `flow` is `conflict-fix`

#### Scenario: CI-failing signal beats confirmation gate

- **Given** `signals.confirmation.gateActive === true`
- **And** `signals.ci.failing === true`
- **And** `signals.conflict.prConflicted === false`
- **When** `route(signals, state)` is invoked
- **Then** the returned assignment's `flow` is `ci-fix`

#### Scenario: Router is total (property)

- **Given** any well-typed `Signals` value generated by fast-check
- **When** `route(signals, state)` is invoked
- **Then** it returns a `FlowAssignment` with a defined `flow` field
- **And** it does not throw

### Requirement: State store MUST enforce single-writer ownership per field

The shared state store MUST reject `writeField(owner, path, value)` calls where `owner !== stateFieldOwnership[path]`. Ownership MUST be declared at feature-registration time via each `FeatureModule.stateFieldOwnership`.

#### Scenario: Unowned field write is rejected

- **Given** `stateFieldOwnership["pr.url"] === "implement"`
- **When** the `confirmation` feature calls `store.writeField("confirmation", "pr.url", "...")`
- **Then** the call throws an ownership-violation error
- **And** the underlying state is unchanged

### Requirement: Event bus consumers MUST be write-only and isolated

The event bus MUST fan events out to consumers (`file-logger`, `posthog`, `tui-stream`, `json-output`) without exposing any mutation API. A consumer throwing during event handling MUST NOT crash the poll loop; the bus MUST catch the error and re-emit it as a `consumer.error` event.

#### Scenario: Crashing consumer does not break the loop

- **Given** the `posthog` consumer throws on every event
- **When** the poll loop emits any event
- **Then** other consumers still receive the event
- **And** a `consumer.error` event is emitted naming `posthog`
- **And** the poll loop continues to the next iteration

### Requirement: Linear attachment capability MUST provide an idempotent `adopt`

The Linear attachments capability MUST expose an `adopt()` operation such that syncing spec attachments twice against an empty Linear state results in exactly one attachment per slot.

#### Scenario: Double-sync yields one attachment per slot

- **Given** a Linear issue with no existing attachments
- **And** a change with attachment slots `proposal`, `design`, `tasks`
- **When** spec attachment sync runs twice in succession
- **Then** the Linear issue has exactly one attachment per slot (three total)
- **And** no duplicates are created
